# DFlash2 at TP=3 — 2026-08-28

First working DFlash2 deployment of GLM-5.3-Flash at **tensor-parallel 3**. Upstream ran
DFlash2 only at TP=2 and TP=4, where the drafter's 32 q / 8 kv heads both divide. Neither
divides by 3, and the KV page geometry then adds a second, independent trap.

Fleet: three DGX Spark nodes; rank 0 serves the API.
Image `glm53:sm121-v12-dflash2`, 512K context, fp8 KV pinned 11.523 GB, RoCE, enforce-eager.

## Three bugs, one per boot

### 1. The mount that reverted the image's patch

The v12 image patches EAGLE3 aux-hidden-state capture into
`vllm/models/glm5next/nvidia/model.py` at build time (`patch_glm_aux_capture.py`). But
`serve.sh` bind-mounts the TP=3 overlay's copy of that same file over it, which reverts
the patch at runtime:

    RuntimeError: Model does not support EAGLE3 interface

Fix: apply `patch_glm_aux_capture.py` to the TP=3 overlay copy
(`$OVERLAY_DIR/glm5next_model_dflash2.py`, 6 edits, ast-clean) and mount that when
`SPEC_METHOD=dflash`. Only `model.py` collides — the other three dflash2 patches touch
`kv_cache_utils.py` and `attn_utils.py`, which `serve.sh` does not mount.

### 2. The drafter cannot shard at TP=3

    qwen3_dflash.py:188  assert self.total_num_heads % tp_size == 0

`draft_tensor_parallel_size=1` does **not** avoid this. `load_dflash_model()`
(`v1/worker/gpu/spec_decode/dflash/utils.py`) builds the draft with
`replace(vllm_config, ...)` and never applies `speculative_config.draft_parallel_config`,
so the drafter always shards at *target* TP. The setting is silently ignored on this path.

Fix: `scripts/pad-dflash2-drafter.py` zero-pads the checkpoint's attention heads.

### 3. The pad that boots is not the smallest pad

The obvious pad is 36 q / 9 kv — smallest that divides 3 while keeping the GQA ratio.
It loads, then dies:

    ValueError: To serve at least one request with the model's max seq len (524288),
    33.62 GiB KV cache is needed ... available 10.73 GiB

Not a head problem — a *page* problem. `patch_glm5_drafter_group.py` slot-shares the
drafter onto the MLA tensors only when its rescaled page exactly fills the MLA page **and**
the two block sizes divide one another:

| pad | kv/rank | B/token | exact-fit block | vs MLA block 4608 | mode | needed @512K |
| --- | ---: | ---: | ---: | --- | --- | ---: |
| 36/9 | 3 | 768 | 3072 | `4608 % 3072 != 0` | standalone | ~20 GiB |
| **48/12** | **4** | **1024** | **2304** | `4608 % 2304 == 0` | **exact fit** | **3.2 GiB** |

In standalone mode the drafter keeps `block_size=16`, and the block count needed to cover
512K explodes. At 4 kv heads/rank the drafter is per-rank geometrically **identical to
upstream's working TP=2 lane** (exact-fit block 2304 = the sim's GEOMETRY A) — the only
configuration proven on hardware. Upstream notes the standalone path "had never run on
real hardware" and is their prime suspect for a chunked-prefill kill.

**Ship 48 q / 12 kv.** Per rank: 16 q / 4 kv, GQA ratio 4 intact.

## Why the pad is safe

q head `i` attends kv head `i//4` throughout, so every real head (`i < 32`) keeps its
original kv head; padded q heads 32–47 read padded kv heads 8–11 and contribute exactly
zero (q=0 gives a uniform softmax over v=0, and their o_proj columns are zero anyway).
`q_norm`/`k_norm` are per-head-dim `[128]` and apply identically to every head.

The script asserts this numerically rather than by argument — it runs one attention layer
with the original and padded weights on the same input and compares o_proj output:

    [verify] layers.0: max|ref-padded| = 0.000e+00  (output scale 1.548e+02)

Bit-identical `model.safetensors` (`0ae7776d…`) generated independently on all three nodes.

## Note on the simulation harness

`overlay-dflash2/sim_glm5_drafter.py` passed for our geometry while the real boot failed.
It calls `_get_kv_cache_groups_glm5_next` **directly**, bypassing `get_kv_cache_groups`'s
dispatch, and it hardcodes drafter `block_size=2048` where the real spec arrives with
`block_size=16`. It is a useful check of the patch's internals, not of whether a config
will boot. What actually resolved this was dumping the real `kv_cache_spec` inventory from
an instrumented boot, then replaying the accounting offline against those exact numbers —
which turns a 12-minute boot cycle into a sub-second sweep.

Real inventory at TP=3, for anyone reproducing:

    x34 MambaSpec         block=4608 page=2359296 padded=2359296
    x11 MLAAttentionSpec  block=4608 page=152064  compress=4   (indexer)
    x11 KpoolTailSpec     block=4    page=2048    window=4
    x11 MLAAttentionSpec  block=4608 page=2359296 compress=1   (MLA)
    x 5 SlidingWindowSpec block=16   page=12288   kv_heads=3   (drafter, 36/9 pad)
